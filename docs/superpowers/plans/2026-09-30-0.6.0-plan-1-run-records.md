# voicecap 0.6.0, Plan 1 of 6: Run Records Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Runs record what the shareable report needs from them: each page's title, every failed attempt with its cause, the listener's statement, and the computer's details.

**Architecture:** New optional fields on the run record (`run.json`, still `schemaVersion: 1`): `PageRecord.title` and `PageRecord.failedAttempts`, `SessionRecord.listener`, and `EnvironmentRecord.machine`. Errors voicecap raises on purpose carry a failure code that `causeOf` reads. A pass reports its failure's code, step, and command, and the page runner turns each failed attempt into a record. The CLI asks the listener's question at a terminal through a callback `runAudit` takes, after the screen reader has stopped and before the run is sealed.

**Tech Stack:** TypeScript (strict, ESM), Node.js 22.19+, Vitest, ESLint and Prettier; PowerShell (Windows) and `sw_vers`, `sysctl`, and `system_profiler` (macOS) for the computer's details.

**Spec:** `docs/superpowers/specs/2026-09-30-shareable-report-design.md`: "New evidence each run records" (D, E, and F), "The human review", and "Problems during the runs".

## The 0.6.0 plans

1. **Run records (this plan):** page titles; failed attempts (E); the listener's statement (F); the computer's details (D).
2. **The page:** the share model, `src/share/text.ts`, `problems.ts`, `check.ts`, `html.ts` and its fonts, and `voicecap share` writing `share/current.html`.
3. **The Word copy and sharing:** `docx.ts`, `current.docx`, the dated copies, `shares.json`, the paste line, and `verify`'s checks.
4. **The walkthrough file:** `voicecap walkthrough`, `--walkthrough`, and the page's download.
5. **The website** (approved 2026-09-30): `voicecap site`, which builds `site/` in voicecap's repository for Netlify to publish as `icjia-voicecap.netlify.app`, and `netlify.toml`, `.nvmrc`, `robots.txt`, and the generated `_headers`.
6. **Stage 2, at the PC:** evidence A (`events.jsonl` and the program in front), B (screenshots), and C (NVDA's own log and the cross-check).

Each plan is written when the one before it lands, so it can build on what that one made.

## Global Constraints

- Node.js 22.19 or later; TypeScript strict; ESM; pnpm. `pnpm lint` (ESLint, then Prettier), `pnpm typecheck`, and `pnpm test` all pass before each commit.
- Records stay `schemaVersion: 1`. Every new field is optional, absent in runs from earlier versions, and read as "not recorded" when absent. The run's seal (`sealOf`) covers the new fields as it covers everything else.
- Times in attempt records are local ISO time to the millisecond, such as `2026-09-30T12:19:24.482-05:00`.
- Never recorded: the computer's maker or model, the Windows account name, or the computer's name.
- A stack trace kept in a record has the home folder replaced: `%USERPROFILE%` on Windows, `~` elsewhere.
- Screen-reader specifics stay in the driver layer and the config. The failure codes are general: `foreground`, `locked`, `screen-reader-stopped`, `browser`, `http`, `open-timeout`, `step-timeout`, `page-timeout`, and `unexpected`.
- Never start a real screen reader, in tests or while building: no run without `--replay-from` or a scripted driver; no `setup`, `doctor`, `test:nvda`, or `fixture:capture`; never pass a composed command through `cmd /c` or any shell.
- Commit messages have no AI trailers: no `Co-Authored-By`, no `Claude-Session`.
- Wording: voicecap is a person's review with a real screen reader, sped up. Never "automated testing" or "automated checker".

## Review Focus

1. **A `run.json` from 0.5.0 or earlier** (no titles, attempts, statement, or machine): resuming it works, and `verify` still passes. Task 3 adds the test.
2. **Ctrl+C a second time while the listener's question is on screen:** the run ends interrupted, records no statement, and nothing hangs. Task 4 adds the test.
3. **Input that isn't a terminal** (a script, CI, piped input): the question is never asked. Task 4 adds the test.
4. **A stack trace with the home folder written another way** (`c:\users\cschw`, `C:/Users/cschw`): it's still replaced. Task 2 adds the test.
5. **A page that fails before any step** (it can't be opened), or on an HTTP 4xx: its attempt record has the pass, no step, and the right code. Task 3 adds the tests.

**Interfaces:**
- Consumes: `FailureCause`, `causeOf`, `redactHome`, `isoLocalMs` (Task 2).
- Produces, in `src/model.ts`:

```ts
/** One failed attempt at a page, kept in the page's record. */
export interface AttemptRecord {
  /** 1-based. */
  n: number;
  /** Local ISO times, to the millisecond. */
  startedAt: string;
  endedAt: string;
  /** The pass under way, or null when the attempt failed before its first pass began. */
  pass: PassName | null;
  /** The 1-based step that failed (its keystroke was discarded), or null outside a step. */
  step: number | null;
  /** The driver command that step sent ("nextLine", "openPage", …), or null. */
  command: DriverCommand | "openPage" | null;
  cause: FailureCause;
  message: string;
  /** For "unexpected" only: the stack, with the home folder replaced. */
  stack?: string;
  /** Whether NVDA and the browser were started again before the next attempt. */
  restarted: boolean;
}
```

  and `PageRecord.failedAttempts?: AttemptRecord[]`, every failed attempt of the page's last processing, oldest first, including the final one of a failed page.
- Produces: `PassResult.failure?: { cause: FailureCause; message: string; step: number | null; command: DriverCommand | null; stack?: string }`, set when the pass stops with "timeout" or "error".
- Produces: `StepRecorder.current: { n: number; command: DriverCommand } | null`, set while a step's driver call is under way.
- Produces: `PageOutcome.failedAttempts: AttemptRecord[]`.
